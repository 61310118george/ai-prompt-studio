## 2026-07-08 - 採用 Codex 官方 surface 管理專案脈絡

- 決策：使用 `AGENTS.md`、`.codex/config.toml`、`docs/` 與 Skill 的方式管理畢業專題協作。
- 背景：使用者要求不要自行編造提示詞架構，而是依照 Codex 官方既定方式設計。
- 選項：
  - 把所有內容寫成單一 master prompt。
  - 依照 Codex surface 分層管理。
- 理由：分層管理更符合 Codex 對短期指令、長期專案規則、設定與可重複流程的設計。
- 影響：後續專案規則會放在 `AGENTS.md`，畢專內容會放在 `docs/`，重複流程會整理成 Skill。
- 後續行動：逐步詢問使用者背景、限制、題目方向與交付要求。

## 2026-07-08 - 專題定位為本機個人工具與畢專簡易版並行

- 決策：此系統第一優先服務使用者本人，目標是能安裝或執行在自己的電腦中，用來管理 AI 記憶與提示詞；同時整理出可提交畢業專題的簡易版本。
- 背景：使用者認為此工具對自己也很實用，不希望只做一個交作業用的展示品。
- 選項：
  - 只做畢專展示系統。
  - 以個人實用工具為核心，再收斂成畢專可展示版本。
- 理由：以使用者自身需求為出發點，可以讓題目更真實、需求更清楚，也更容易做出可 Demo 的成果。
- 影響：技術選型應優先考慮本機可執行、資料可保存、單人使用穩定；雲端部署與多人協作可延後。
- 後續行動：確認第一版應該是桌面應用、網頁本機應用，或其他形式。

## 2026-07-08 - 第一版目標平台選擇 macOS 桌面應用程式

- 決策：第一版設計成 macOS 桌面應用程式。
- 背景：使用者的電腦是 Mac，並希望此工具能像一般 App 一樣在自己的電腦中使用。
- 選項：
  - 桌面應用程式。
  - 本機網頁系統。
  - 先做功能原型再決定包裝形式。
- 理由：桌面應用程式更符合使用者想長期管理個人 AI 記憶的使用情境。
- 影響：後續技術選型需要評估 macOS 桌面 app 的開發方式，例如 Python 桌面框架、Electron/Tauri、或先用本機服務加桌面殼。
- 後續行動：選擇適合使用者技術背景與畢專時程的桌面 app 技術方案。

## 2026-07-08 - 採用 Python 桌面 App 方向

- 背景：使用者目前最熟悉 Python，且希望 App 能在自己的 Mac 上使用。

  - Python 桌面 App。

- 影響：後續需要選擇具體 GUI 框架，例如 PySide6、PyQt 或 Tkinter。
- 後續行動：評估 Python GUI 框架並選定第一版技術組合。

## 2026-07-08 - 第一版 GUI 框架預設採用 PySide6

- 決策：第一版 Python 桌面 App 預設採用 PySide6。

- 理由：PySide6 適合做正式桌面 UI，介面彈性高於 Tkinter，且比 Electron/Tauri 更符合使用者目前 Python 背景。

## 2026-07-08 - 專題人力以使用者為主要實作者

- 決策：專題規劃與實作以使用者為主要實作者，Codex 協助設計、拆解、實作與文件整理；其他組員主要承擔報告、資料整理或輔助工作。
- 背景：使用者表示大部分內容會由使用者與 Codex 完成。
- 理由：後續範圍評估必須以實際可投入的工程人力為準，不能假設小組成員能分擔核心開發。
- 影響：技術選型、功能數量、架構複雜度與時程都應保守控制。
- 後續行動：確認學校要求與期限，建立可完成的最小可行版本。

## 2026-07-08 - 核心功能離線可用，AI API 作為可選功能

- 決策：第一版核心記憶管理功能不依賴 API Key；AI 精簡與整理功能需要使用者自行填入 API Key 才能使用。
- 背景：使用者希望盡量不要額外花錢，也避免 App 被付費 API 綁死。
- 理由：此設計可以降低成本風險，並確保畢專 Demo 即使沒有 API 或 API 出問題也能展示核心系統。
- 影響：資料管理、提示詞組合與版本紀錄必須本機可用；AI 功能需設計成可開關、可替換、可降級。
- 後續行動：確認本機資料儲存方式，預設評估 SQLite。

## 2026-07-08 - 第一版本機資料庫預設採用 SQLite

- 決策：第一版本機資料庫預設採用 SQLite，並保留資料匯出功能。
- 背景：使用者熟悉 Sequel Ace，但表示其餘資料庫選型可由 Codex 決定，重點是資料要能讀得到。
- 理由：Sequel Ace 主要用於 MySQL/MariaDB；若第一版為了配合 Sequel Ace 改用 MySQL，會增加本機資料庫服務安裝、啟動、設定與維護成本。SQLite 更符合 macOS 本機桌面 App、低成本與三個月 MVP 目標。
- 影響：App 內部資料以 SQLite 儲存；若使用者需要檢查資料，可透過 SQLite viewer 或匯出 CSV/Excel 檔查看。
- 後續行動：後續資料模型設計以 SQLite 為基準。

## 2026-07-08 - AI 工具規則升級為模板轉換功能

- 決策：AI 工具規則不是單純記憶分類，而是第一版系統需要內建的模板轉換功能。
- 背景：使用者指出每個 AI 軟體都有自己的規則，因此系統應能根據不同情境自動轉換成 AI 可以理解的模板。
- 理由：這是本專題與一般提示詞筆記工具的主要差異，可形成畢專核心價值。
- 影響：資料模型需要支援工具模板、模板版本、適用情境、輸出格式與來源記錄；第一版需限制支援範圍，避免承諾所有 AI 平台。
- 後續行動：定義第一版要支援哪些 AI 工具模板，初步建議 Codex、通用 ChatGPT、Claude。

## 2026-07-08 - 第一版 AI 工具模板支援 Codex、ChatGPT、Claude

- 決策：第一版 AI 工具模板轉換器支援 Codex、通用 ChatGPT、Claude。
- 背景：使用者同意先支援三種核心 AI 工具模板。
- 理由：Codex 是目前專案協作主工具，ChatGPT 通用性高，Claude 可代表另一類 AI 協作工具格式。
- 影響：第一版不支援 Cursor、Windsurf、Gemini、Perplexity 等工具；可作為第二版擴充項目。
- 後續行動：設計模板資料表與輸出格式。

## 2026-07-08 - AI 工具模板不作為前台主分類

- 決策：AI 工具模板屬於內建輸出/轉換功能，不放入前台主要內容分類頁籤。
- 背景：使用者指出 AI 工具模板已是系統內建功能，不應被設計成前台主題標籤。
- 理由：前台主分類應服務使用者管理記憶內容；工具模板則應在「產生提示詞」或「匯出」時作為目標格式選項。

## 2026-07-09 - AI 整理器接入 OpenAI Responses API

- 決策：AI 整理器支援使用者自行輸入 OpenAI API Key 呼叫 Responses API；沒有 API Key 時仍使用離線整理模式。
- 背景：第一版需要 AI 精簡/整理功能，但使用者希望不要把付費服務設計成必要條件。
- 理由：可選 API 設計保留核心功能離線可用，也讓需要時能展示 AI 自動整理能力。
- 影響：API Key 不保存到資料庫；每次開啟 App 若要使用 API 需重新輸入。OpenAI API 會依使用者帳號計費。
- 後續行動：後續若需要長期使用，可評估 macOS Keychain 儲存 API Key。

## 2026-07-09 - 修正 UI 文字與背景對比度

## 2026-07-12 - 將主功能轉向資料夾式 Markdown 記憶管理

- 決策：新增「資料夾記憶」作為第一順位主畫面，支援選擇根資料夾、讀取專案資料夾、讀取 `.md` 記憶檔、產生修改預覽、顯示 diff 並寫回 Markdown。
- 背景：使用者希望 App 不只是資料庫式管理，而是能管理某個根目錄下依專案分類的 AI 記憶與提示詞 Markdown 檔。
- 理由：Markdown 資料夾結構更接近 Codex、Claude、ChatGPT 等 AI 工具的實際提示詞/記憶管理方式，也更能凸顯 App 的價值：可視化管理、清楚知道改動、降低重複溝通成本。
- 影響：原本 SQLite 記憶管理保留，但不再是唯一核心；App 的主要差異化功能轉向「Markdown 記憶工作區」。
- 後續行動：補正式 AI 修改流程、更多 diff 呈現、token 節省估算與 AI 工作進度視覺化。

## 2026-07-17 - 增加新專案 AI 初始化與任務分派文檔方向

- 決策：將「預設問題模板」與「專案 AI 初始化文檔產生」納入後續功能方向。
- 背景：使用者希望 App 除了能可視化檢查 AI 記憶邏輯，也能先設定多種協作情境，例如「多人 AI 協作」或「單人 AI 協作」，再由 App 產出可交給本次專案 AI 的文檔。
- 選項：
  - 只管理既有記憶與提示詞。
  - 加入新專案初始化流程，讓 App 先引導使用者回答關鍵問題，再產出專案啟動文檔。
- 理由：此功能能把 App 從「提示詞資料管理工具」提升為「AI 協作設定工具」，更能凸顯畢專價值，也能解決每次開新專案都要重新向 AI 說明背景與分工的問題。
- 影響：後續資訊架構需要新增或調整出一個「專案初始化」或「任務分派」流程；資料模型可能需要儲存問題模板、回答紀錄、協作模式與輸出文檔。
- 後續行動：先定義第一版預設問題組，建議從單人 AI 協作、多人 AI 協作、畢業專題開發三種情境開始。

## 2026-07-17 - 實作第一版專案初始化頁

- 決策：新增「專案初始化」作為主導航第一個功能頁，第一版先採離線固定模板，不新增資料庫 schema。
- 背景：使用者要求開始實作新專案 AI 初始化與任務分派文檔產生功能。
- 選項：
  - 先只寫規格，不做 UI。
  - 先做可操作的離線模板產生器。
  - 直接做 API 驅動的動態問答流程。
- 理由：離線模板產生器能快速形成可 Demo、可實際使用的功能，且不依賴 API 成本；固定模板也方便後續調整問題品質。
- 影響：App 主導航由早期內容管理為主，擴充為「新專案啟動 -> 記憶管理 -> 提示詞整理」流程；第一版支援單人 AI 協作、多人 AI 協作、畢業專題開發三種情境。
- 後續行動：後續可加入回答儲存、模板編輯、AI 自動追問、token 節省估算與不同工具的輸出格式差異化。

## 2026-07-19 - 2.0 改採 Web 與桌面共用介面

- 決策：以 pywebview 載入正式 HTML、CSS、JavaScript 前端，不再將 Web 原型人工重寫成 PySide6 畫面。
- 背景：使用者希望先在 Web 完成 UI，再直接複用到 macOS App。
- 理由：單一前端可消除兩套 UI 的同步成本，同時保留既有 Python、SQLite 與 Markdown 服務。
- 影響：`web-preview/` 升級為正式前端；PySide6 UI 保留為 legacy 回退。

## 2026-07-19 - 2.0 核心定位為 Agent 記憶編程

- 決策：主導航重整為專案、記憶編程、記憶健檢、設定。
- 背景：原本六區較像一般提示詞與資料管理工具，沒有聚焦「看懂 AI 實際會載入哪些記憶檔」。
- 理由：以專案與 Agent 原生檔案為核心，更能解決使用者無法檢查有效上下文的痛點。
- 影響：第一版正式支援 Codex、Claude Code、Gemini CLI、OpenClaw；舊資料保留但不再各自佔用主導航。

## 2026-07-19 - 離線結構化 compiler 取代必要 AI 改寫

- 決策：使用結構化欄位與固定 renderer 產生 Markdown，不把自由文字智慧改寫列為核心能力。
- 背景：使用者希望本機免費使用、不消耗額外 AI token。
- 理由：沒有模型時，結構化表單比假裝理解語意更穩定、透明且可測試。
- 影響：App 清楚區分「格式化」與「語意改寫」，必填欄位、條列與 code block 都可離線驗證。

## 2026-07-19 - 檔案修改採 managed section 與可復原安全策略

- 決策：只管理 HTML comment 標記區段，並加入 Diff、SHA-256、atomic write、備份與復原。
- 背景：直接覆蓋整份記憶檔可能刪除使用者或其他 Agent 維護的內容。
- 理由：區段合併可維持可讀性並把破壞風險降到最低。
- 影響：若檔案在預覽後改變，App 必須停止寫回；路徑必須限制於已授權根目錄。
